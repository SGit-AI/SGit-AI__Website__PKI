# pki.sgit.ai — a register of people and their public keys

Find someone and send them something only they can read. A person registers a passkey on the
site, which opens a vault (the newsroom's door → master → book design); makes a key pair in the
browser, byte-compatible with `sgit pki`, or imports sgit's; publishes the public half as a signed
record; adds evidence (website, GitHub, DNS); is verified by an anchor (Dinis Cruz, for now); and
links with the people they know. **A link counts only when both records hold one**, each written
by its owner in their own record: the answer to how the old web of trust was flooded in 2019.

Since v0.2.0 (18 October 2026) people come first. Everything the site designed for agents from
August to October 2026 is kept, under `archive/`, and the four registry rules carry over unchanged.

Live site: https://pki.sgit.ai (GitHub Pages, deployed from `dev`).

## The register of people

- `people/` — the register (`index.html`), one person (`person.html#sha256-<16 hex>`), how it works
- `vault/` — your vault: keys, record, links, contacts, inbox, doors
- `send/`, `m/` — seal a message to someone (link + QR code, or their inbox); open one
- `invite/`, `join/` — invitations by QR code, and where they land
- `directory/records/sha256-<16 hex>/NN__<type>.json` — the signed statements, one per file (the source)
- `directory/index.json` — generated by `admin/build/people.mjs build`; `anchors.json`; `fixtures/` (published private keys)
- `assets/people/` — the code, shared by the pages, the build and the tests: `keys.js` (sgit-compatible
  keys, PEM/PBES2, the hybrid v2 envelope, statements), `directory.js` (records, two-way links, the
  graph), `message.js` (messages, m1 links, invitations), `account.js` (door/master/book, the inbox),
  `door.js` (the newsroom's, with pki.sgit.ai's constant), `evidence.js`, `ui.js`, `pages/`
- `assets/vendor/` — the vault library, the newsroom's vault module and the QR generator, unchanged, with hashes

Adding someone's record: `node admin/build/people.mjs add <submission.json>` (checks every signature and
that every statement is the record's own, writes nothing otherwise), then release as below.

Tests: `node admin/build/test_people.mjs` (with `pip install sgit-ai`, also against the CLI),
`node admin/build/test_people_vault.mjs` (mock vault server), `node admin/build/test_people_browser.mjs`
(Chromium, virtual passkeys with PRF, two people end to end).

## Structure (the rest of the site)

- `index.html` — front page: people first (the August front page is `archive/front-2026-08.html`)
- `archive/` — what the site was, kept: the agent register and everything around it
- `failure/` — the 2019 keyserver failure, with sources; the append-only resolution
- `bootstrap/` — the bootstrap trap: why agent key registries do not exist
- `rules/` — the four registry rules, published before the registry exists
- `mandate/` — identity and mandate as separate, independently revocable statements
- `enrolment/` — how a key gets in, starting from a keypair and nothing else
- `execution/` — the execution broker, and receipts as the third corner
- `shipped/` — what already ships, what is only proposed, and the two absences
- `roadmap/` — the build order, the honest tensions, the open questions
- `documents/` — the source briefs, readable in-page (raw markdown is the source of truth)
- `briefs/` — those source documents, captured verbatim
- `about/participant.html` — the participant disclosure, and where our approach loses
- `admin/` — engineering: comms (tasks & requests), versions, build tooling
- `admin/build/chrome.py` — the single definition of nav and footer, applied across every page
- `admin/build/gen_documents.py` — generates the `documents/` reader pages
- `admin/build/gen_records.py` — generates one identity-card page per registry record
  (`registry/records/<fp>/index.html`); the JSON files beside it stay the source of truth
- `assets/site.css` — shared stylesheet (sgit.ai design language)

Content was refactored across from the PKI section of
[nhi.sgit.ai](https://nhi.sgit.ai/pki/index.html), where it was staged, and promoted from
three pages to a site.

## Release process

1. Bump `admin/build/version.txt` (vX.Y.Z, exactly once per release) and add a row to
   `admin/versions.html`; update `admin/comms.html`.
2. `node admin/build/people.mjs build` if a record changed; `python3 admin/build/chrome.py` — propagates the version badge and any nav/footer change
   to every page. (`gen_documents.py` first, if a document was added; `gen_records.py`
   if a registry record changed.)
3. `node admin/build/validate.js`
4. `git commit -am "site vX.Y.Z: ..." && git push origin dev` — the `site vX.Y.Z:`
   prefix is load-bearing, not decoration: `tag-release` finds the release commit by
   scanning subjects for it, and refuses the release when the newest one it finds
   disagrees with `version.txt`. A subject in any other shape fails the job after the
   push, and nothing deploys until a commit carrying the prefix lands.

Every push to `dev` runs `.github/workflows/deploy-pages.yml`: validate → auto-tag
(`vX.Y.Z`, verified against version.txt and the commit subject, next-minor enforced) →
deploy to GitHub Pages. Pull requests run validation only. Same pipeline as
[SGit-AI__Website](https://github.com/SGit-AI/SGit-AI__Website) and
[SGit-AI__Website__NHI](https://github.com/SGit-AI/SGit-AI__Website__NHI).
